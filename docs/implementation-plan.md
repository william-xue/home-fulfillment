## 1. 项目目标与边界

- **业务：** 一家家居品牌，自营商城与抖音小店共享库存，上海仓（华东）优先、广州仓（华南）补充。首版面向运营、仓管、客服；不是商城前台。

- **最终操作体验：** 在工作台打开一个渠道单号，点到它的订单行、预占、仓库作业、发货事实和运单；再用 DataGrip 按同号查 MySQL，并定位到实际写入的 Java 方法。

## 2. 先按这些规则实施

下列是**首版业务摘要**；完整规则见 V1 规格。不要照搬旧项目里的不同口径；无法满足验收时报告影响，不静默改规则。

| 决策 | 首版规则 |
|---|---|
| 接单时点 | 只接声明已支付的模拟渠道单，不实现未支付状态或支付超时；支付是上游事实，不是本系统收款。 |
| 重复接单 | 同一 `(channel, channel_order_no)` 加唯一约束。相同业务内容重放返回原单；同键不同 SKU / 数量等有效载荷报冲突，不覆盖原单。 |
| 收货、上架 | 一张采购单订 10 可先收 8；按行累计、禁止超收。收货只进暂存位，只有上架到可拣位才进入可分配库存。两个库位间转移同事务写负/正两条流水。 |
| 选仓、拆单 | 同一订单行允许按数量拆到两个仓：上海先用、上海不足广州补齐；每仓一张履约单。两仓加起来不够满足**整张订单**时，OMS 保留 `SHORTAGE`，不留下部分预占或半张履约单。补货后允许对原单重试路由。 |
| 库存口径 | 库存模块持有库位余额与流水，首版按 SKU × 仓 × 库位唯一。仓级可分配量由可拣库位的 `on_hand - reserved` 求和，暂存、非良品位不参与，不另维护一套仓级可售真值。 |
| 预占、拣货、出库 | 预占只增 `reserved`；拣货确认只写任务进度，货仍属本仓待出库，账面 `on_hand` 与 `reserved` 不变，不能卖第二次。首版不独立维护打包暂存位账，行的源库位余额直到出库确认才扣。出库确认同事务扣 `on_hand` 与 `reserved`、记流水与发货事实；库位账此处不是实时货架定位。 |
| 取消 | 首版仅允许**所有履约单均未开始拣货且未出库**的整单取消，原预占同事务释放；一旦开始拣货，拒绝取消并解释原因，不实现撤拣或退货。`SHORTAGE` 单取消不做库存变更。 |
| 履约与运输 | 发货是仓库事实，签收是运输事实。任一仓发货不能把整单标为全部已发；全部应发数量出库后才聚合为已发。已出库可由本地运输操作建单、追加轨迹；每张履约单一个运单，未出库不能建，终态签收不能由迟到事件改回在途。 |

**数据所有权：** OMS 写渠道订单和路由结果；库存模块独占库存余额、预占明细和流水的写权限；WMS 写入库/出库单据、库位作业与拣货任务，仅通过库存用例记账；TMS 写运单/轨迹，不改库存；前端和查询接口不推导第二套状态真值。允许同库事务协调跨模块写入，不允许跨模块直接调用对方 Mapper。

**事务底线：** 预占、取消、出库使用 MySQL 状态闸和数量条件，不靠 Redis 保证不超卖。路由锁定后先算完整方案，确认缺货才提交 `SHORTAGE`；技术失败整笔回滚，不能当作缺货。锁顺序、重试边界、表约束与幂等以 V1 规格为准。

## 3. 技术与运行约束

| 组件 | 建议与加入时机 |
|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Element Plus，优先支持单据详情、状态、操作入口和异常提示。用一套已验证的包管理器并提交锁文件。 |
| 后端 | Java 17 + Spring Boot + MyBatis。一个可部署后端、按业务分包；不做微服务、网关或公共框架。依赖版本先查兼容性再锁定，不照搬旧 POM。 |
| MySQL | 独立 MySQL 8.x 实例/库，Flyway 迁移；应用账号不连 root，不连旧库。演示数据隔离且支持重复启动，迁移与初始化不因启动覆盖业务数据。 |
| Redis | 到 M4 再加。建议缓存运营首页的只读汇总，短 TTL，故障时回 MySQL；库存校验和详情不依赖 Redis。 |
| MQ | 到 M4 再加，首选沿用 RocketMQ 经验，需验证本机镜像和启动成本，不通过就先保留 outbox 设计并交代阻塞，不默默切换依赖。示例消费链：出库事件 → 自动创建运单，消费去重，并允许异常后继续重试。早期手动建运单与自动创建走同一幂等用例。 |
| Elasticsearch | 暂缓。首版按单号、状态、渠道用 MySQL 查询；确有查询需求和测量证据才评估 ES。 |
| 本地运行 | Compose 管新项目 MySQL，后续增加 Redis/MQ；只绑定本机。开发态提供一个启动与健康检查入口，最终支持按 README 从干净目录启动。建议前端 `5180`、后端 `8090`、MySQL `43307`，先查占用再定。停止命令只停本项目，不删数据卷。 |
| 权限与观测 | M1 就给运营、仓管、客服基础账号和写接口权限，仓管只能操作授权仓。每次写入记录操作者/时间，错误能按请求 ID 或单号查日志。不提交密码，演示账号仅本地使用。 |

## 4. 阶段与验收

每个阶段都沿着同一个项目扩展。交验至少留：**可运行命令、浏览器操作、同号 SQL、核心 Java 方法、已通过测试与未验项**。API 成功不等于页面通过，旧数据回读不等于新功能实跑。

### M0 — 环境与骨架

- 检查目标目录、端口、Docker daemon、Java/Node 与包管理器；确定依赖版本和独立数据卷。
- 建前后端和本地启动入口；只建 M1 用得到的模块；编写运行说明、环境示例、健康检查、数据库迁移；检查应用连接的是**新** MySQL。
- **验收：** 空库迁移成功，重复启动不会增加或重置记录，前端能通过代理访问后端；记录真实端口及 DataGrip 连接信息，不写密码。Docker 启动失败时停在 M0，不把 mock / 旧库当完成。
- **检查命令：** 在目标目录启动前核对 `docker info`、`docker compose version` 和 `docker compose config --quiet`；启动后执行 `curl -fsS http://localhost:8090/actuator/health`（如端口改了，用实际端口）。仅有 HTTP 200 不够，还要确认健康结果及数据库名称对应新项目。

### M1 — 第一条业务切片：部分收货 → 上架

- 用页面完成：仓管登录 → 打开种子采购单 `PO-HOME-001`（上海仓，`HOME-BOX-01` 订 10）→ 收 8 到 `RECV-01` → 上架 8 至 `A-01-01` → 库存页按 SKU 或单号看账。
- 仅交付采购单详情、收货/上架操作、库存/流水和对应权限。种子作为这条链的起点，不提前塞入成功的收货/上架记录。
- **验收①：** 采购行已收 8、欠 2、单据 `PARTIAL`；收货后暂存现存 +8、可分配不变；上架后暂存 −8、拣货位 +8、同仓现存不再增加。由同一 `receiptNo`、`putAwayNo` 查业务事实与流水。
- **验收②：** 同号同内容重复只写一次，同号不同内容报冲突，拟额外收 3 时拒绝且收货、余额和流水不变；无仓库权限不能写。
- **本次交验停点：** 用真实浏览器完成验收①，至少用集成测试覆盖验收②；输出链接、单号、查询和测试结果。未验证项如实写，**不要先做 OMS、TMS、Redis 或 MQ**。
- **构建与测试：** 从后端目录执行 `./mvnw verify`（交付 Maven Wrapper）；从前端目录按锁文件安装依赖并跑类型检查和构建，例如选 npm 时执行 `npm ci`、`npm run typecheck` 和 `npm run build`。库存写入相关集成测试用独立 MySQL 测试库，不拿大量 Mock 或 H2 代替 MySQL 事务验证，不清空演示库。

### M2 — 已支付渠道单 → 路由与预占

- 新增 OPS 新建采购单、订单列表/详情、渠道接单模拟、优先两仓路由、预占、缺货重试和未拣取消。接 M1 的同 SKU；用同一个收货/上架流程给广州仓备货，不能用人工改余额代替浏览器验收。独立测试夹具仅用于测试。
- **验收：** 上海 8、广州 4 时，同 SKU 订 10 得两个履约单：上海 8 / 广州 2；预占前后现存不变。两仓合计不足时，订单 `SHORTAGE` 且无遗留预占，补货后原单可再路由。两渠道同时抢同一仓最后一件，最多一张获得完整预占，另一张缺货，不出现负可分配量。用真实 MySQL 的独立事务跑并发测试。

### M3 — 仓库履约、取消与运输

- 给 M2 已有预占补拣货任务，新增拣货、出库、基于实际拣货状态的取消闸门和运输查询；订单详情串起履约进度、发货事实、运输轨迹。早期通过本地操作建运单，不假装有承运商对接。
- **验收：** 一仓发货后整单为部分已发；第二仓完成才为全部已发。拣货时余额不扣；出库幂等扣一次并能查对应流水。取消未拣单后余额不减、预占回到可用；已拣或已出库拒绝取消。未出库拒建运单，重复创建不多建，签收后不会因迟到事件回退。
- **竞争用例：** 同一订单并发开始拣货与取消，测试最终只能出现“取消且零拣货”或“已开始拣货且取消被拒”之一，不能两者都成功。聚合根和相关履约单的写入串行化；聚合按实际履约数量，不按最后一条事件覆盖。

### M4 — 可靠事件、运行交付与回归

- 业务事务内写 outbox；后台投递到 MQ；消费端用稳定事件 ID 去重，建运单用履约单号唯一兜底。区分待投递、成功、失败/可重试，不把 MQ 发送成功写成下游已处理。Redis 只做前述读缓存。
- **验收：** 模拟本地 MQ 暂时不可用，出库事实已提交，事件仍可追踪，恢复后最终建单；重复投递不多建运单。Redis 不可用时查单和交易继续，汇总回退 MySQL。
- **交付：** 从干净环境按 README 启动，跑通一笔 `PO → 收货 → 上架 → 渠道订单 → 两仓履约 → 出库 → 运单/签收`；用浏览器、MySQL、Java 三处证据证明。记录备份与恢复，在**另一套隔离库**做一次恢复验证。未做公网安全加固、外部对接及容量测试前，不标注“可生产上线”。
