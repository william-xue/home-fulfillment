# 学习入口｜拿到供应链全栈能力

这个项目不是让你背 Spring，也不是让 AI 帮你演示一遍。假定你有资深前端和 Java 全栈基础；要验证的是：**面对供应链需求，能自己把它拆成单据、状态、表、接口、写入事务和异常测试，最后能维护。** 面试是第二条线，见 [面试训练](interview.md)。

每天只打开本页，先看「下一步」。工程是否已交验看 [TASK-v1](TASK-v1.md)，不要把模型验收当作已学。

## 下一步

**尚无摸底评分。** 已确认主工作台收货并上架 1 件；这只证明页面操作。先走 S3（用这一件录单、路由、拣货、出库、签收），再练 S4：用 [同号 SQL](../infra/mysql/verify-m4.sql) 把「出库已提交、Broker 已确认、运单已经生成」分成三个事实，找出分别在哪张表确认。想亲手改一个失败用例，可在隔离测试里模拟投递器拿到 ACK 就退出，核对再次投递不会多建运单。你说「开始摸底/考我」才做闭卷。

## 摸底：先找断点，不从头学

每题先保留你自己的初答，然后核证和复做。不知道可以标「未做过」，不要背标准答案。尚未有对应代码的题只评设计，不能评为已具备实作能力。

| 题 | 给你的条件与动作 | 看什么能力 |
|---|---|---|
| D1 | PO 订 10，到 8，先上架 3。画采购单/行、收货、上架与余额/流水的关系，再写两个库位的现存、预占和可分配。若再收 3 或再上架 6，哪个字段/条件先拦？ | 能否从业务语言直接转成单据、粒度、状态和 SQL 约束。 |
| D2 | 假设「收 8」请求超时，浏览器重试。指出重复请求和第二次真收货的区别；给一个会证明事务没写脏的测试。 | 能否从页面请求一路到 Java 事务、条件更新、唯一键、验证。 |
| D3 | 上海 8、广州 4，整单订 10。再换成第二行 SKU 缺 1 件：画成功与失败两种落表。两单抢同一件时，为什么前端列表看见可用不算抢到？ | 能否针对此项目区分仓路由、库存真值、锁和部分成功。 |
| D4 | 订单两个仓，一个已拣、一个未拣，这时取消；再把场景换成出库成功但 MQ 挂了。分别判断写不写库存、哪张单据要变、怎么查异常。 | 能否区分状态归属、事务内失败、异步失败和恢复策略。 |
| D5 | 用 60 秒讲一个你确实参与过的开发点，再接受两层追问：为什么这么设计，怎么验证。没有项目实现时可用已有经历，但不伪称是本项目。 | 能否证明个人贡献而非复述技术栈。 |

**评分**：`未测` 不是 0；`1 看材料能定位`、`2 不看能重画并预测数据`、`3 能独立做一个改动并补一个失败测试`、`4 换条件能做取舍并验证`。D5 的 3 是「两层追问都能落证据」，4 是「换业务前提还能判断方案何时失效」。当前 D1–D5 全部未测，不预填分数。首轮只取最低、且影响当前切片的一处补，不追求做完整套卷。

## 从 M0 到 M4 的练习

每次约 20–30 分钟：先在页面找同号，再在 DataGrip 查同号，再找 Java 读写点；最后做一个由你决定或亲手实现的变化。**下表是训练计划，不是能力评级。** 阶段未实现时先纸面预演，不假定界面已存在。

| 练习 | 跟做：观察一笔业务 | 独立改动或迁移题 | 能讲清的标准 |
|---|---|---|---|
| S0 / M0 运行排障 | 用浏览器打开 `/api/health`，跟 Vite → Actuator → MySQL；运行 `verify-m0.sql` 看库名和迁移版本。 | 不改旧服务，在本项目开发配置排查“后端端口正常、页面仍显示不可用”；先列证据，再换一个本项目端口验证。 | 能定位端口/代理、Java 启动、数据库认证、Flyway 四类问题。 |
| S1 / M1 收货与上架 | PO 订10收8，核对头/行、收货号、暂存和上架双边流水。 | 拆成上架3和5；自己补「再上架1拒绝、账不变」用例。先写字段和事务顺序，再写最小代码/测试。 | 能用同号解释超收、重复请求、余额与流水；知道失败时哪些行必须一起回滚。 |
| S2 / M2 拆单与超卖 | 上海8、广州4，单要10；找两履约与各库位预占。 | 另取隔离测试单：第一行够、第二行缺1，逼出“半单污染”测试；再加并发抢最后一件。 | 能指出同一订单与跨订单分别在哪串行，知道为什么不靠 Redis 防超卖。 |
| S3 / M3 出库、取消与运输 | 先拣再分仓发，从订单页跟到库存、发货事实、运单轨迹。 | 写一条并发「确认拣货 vs 取消」的失败用例；再画如果以后允许撤拣，需要新增哪些库存动作。只做设计，不往 V1 偷加功能。 | 能解释不同状态归属、为何拣货不扣账、为什么一次签收不能结整单。 |
| S4 / M4 可靠事件与恢复 | 在隔离环境断 MQ，再恢复，沿 dispatchNo / eventId 查 outbox、inbox 和运单。 | 自己选择并验证「发布成功后进程崩溃」或「人工建单与消费竞争」；另外说清缓存挂了为何不影响预占。 | 能解释至少一次、去重、手工补偿，以及哪里发生过而哪里只是设计演练。 |
| S5 / 结课 | 用没背过的样例，从真实需求写出页面、状态、ER、API、事务和失败用例。 | 独立实现一个有业务不变量的切片或异常路径。先交自己的设计和失败测试；AI 只评审、给提示。最后做 [面试模拟](interview.md)。 | 不靠提示能把需求变成可维护代码，能证实自己做了哪一部分并解释未覆盖边界。 |

**每次拔高只加一项**：只会照步骤就改变数量/状态；能复述就自己补失败测试；能独立改就问「换约束，哪条规则要重新设计」。20 分钟卡住，记具体单号和停点，下次继续同一题。不要用堆中间件掩盖基础业务问题。
